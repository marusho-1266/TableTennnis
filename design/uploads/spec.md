# Spec: 卓球試合記録・分析アプリ

## 1. Objective

### 1.1 目的

卓球の試合を1点単位で素早く記録し、試合後に得点・失点の事実をゲーム別および試合全体で振り返れる、スマートフォン向けWebアプリ（PWA）を構築する。

### 1.2 対象ユーザー

- 自分の試合を記録する選手
- チームメイトの試合を観戦しながら記録する人

### 1.3 中心価値

- 試合中に迷わず、1点を最大3タップで記録できる
- 記録した全ポイントを、試合後に客観的なデータとして確認できる
- 通信環境やアカウント登録に依存せず、その場ですぐ使える

### 1.4 ユーザーストーリー

- 記録者として、ラリー間の短い時間で得点または失点を記録したい
- 記録者として、誤入力した直前のポイントを取り消したい
- 選手として、ゲームごとの得点・失点傾向を確認したい
- 選手として、全ポイントを時系列で見返したい
- 利用者として、過去の試合結果を同じ端末で再表示したい

## 2. Scope

### 2.1 初版に含める

- 記録対象選手名と対戦相手名の入力
- 5ゲームマッチ（3ゲーム先取）
- 1ゲーム11点、10-10以降は2点差がつくまで継続
- 1点最大3タップのポイント記録
- ゲーム／試合終了の自動判定
- 連続Undo
- 試合中の現在スコアと読み取り専用ポイント履歴
- 試合終了後の結果、ゲーム別集計、全体集計、ポイント履歴
- 過去試合の一覧と詳細表示
- 端末内への永続保存
- オフライン利用可能なPWA

### 2.2 初版に含めない

- ユーザー登録、ログイン、複数端末同期
- クラウド保存
- サービス権およびサービス順の記録
- 過去ポイントの分類編集、任意削除
- Undoのやり直し（Redo）
- CSV、JSON、画像などへの書き出し／読み込み
- 動画の撮影、保存、解析
- 課題、敗因、練習メニューの自動分析・提案
- チームや選手ごとの横断集計
- 3ゲームマッチ、7ゲームマッチなどの形式選択

## 3. Functional Requirements

### 3.1 試合開始

1. 利用者は次の項目を入力する。
   - 記録対象選手名（必須）
   - 対戦相手名（必須）
2. 前後の空白を除去し、空文字の場合は開始できない。
3. 「試合開始」を押すと、第1ゲームを0-0で開始する。
4. 試合日時は端末時刻から自動記録する。
5. 進行中の試合がある場合は、新規試合を開始する前に確認を表示する。

### 3.2 ポイント入力の共通ルール

1. 第1タップで「得点」または「失点」を選ぶ。
2. 第2タップで大分類を選ぶ。
3. 詳細分類が必要な大分類だけ、第3タップで詳細を選ぶ。
4. 詳細分類がない大分類は、第2タップ時点で記録を確定する。
5. 確認ボタンは設けず、最後の分類をタップした時点で確定する。
6. 未確定の分類選択中は、1つ前の階層または得点／失点選択へ戻れる。
7. 連打による同一ポイントの二重登録を防止する。

### 3.3 得点分類

| 大分類 | 詳細分類 | 確定タップ数 |
|---|---|---:|
| サーブ | エース、相手レシーブミス | 3 |
| 3球目 | フォアドライブ、フォアドライブ回り込み、バックハンド、スマッシュ、その他 | 3 |
| ラリー（5球目以降） | なし | 2 |
| レシーブ | フォアドライブ、バックハンド、相手ミス、その他 | 3 |
| 相手ミス | サーブミス、レシーブミス、攻撃ミス、その他 | 3 |

表記は「バックドライブ」ではなく「バックハンド」に統一する。

### 3.4 失点分類

| 大分類 | 詳細分類 | 確定タップ数 |
|---|---|---:|
| サーブミス | ネット、オーバー、空振り、その他 | 3 |
| レシーブミス | ネット、オーバー、空振り、その他 | 3 |
| 3球目ミス | フォアドライブネット、フォアドライブオーバー、バックハンドミス、空振り、その他 | 3 |
| ラリー | なし | 2 |
| 相手決定打 | レシーブ浮いた、その他 | 3 |

### 3.5 スコアとゲーム進行

1. 得点を確定すると記録対象選手のスコアを1増やす。
2. 失点を確定すると対戦相手のスコアを1増やす。
3. 10点未満の相手に対して11点以上へ到達した側がゲームを取得する。
4. 10-10以降は、2点差がついた側がゲームを取得する。
5. ゲーム終了時に入力を停止し、ゲーム番号、最終スコア、ゲーム取得者を表示する。
6. 第1〜第4ゲームの終了後、試合勝者が未確定なら「次のゲームへ」で次ゲームを0-0から開始する。
7. 3ゲームを先取した側を試合勝者とし、試合を終了する。
8. 試合終了後は「試合結果を見る」で試合後画面へ移動する。

### 3.6 Undo

1. 進行中の試合では、記録済みポイントがある限り直前の1点を取り消せる。
2. Undoを繰り返し、複数ポイントを1点ずつ連続して取り消せる。
3. ゲーム終了後でも、次ゲームの最初のポイントが未入力なら直前ゲームの最終ポイントを取り消せる。
4. 次ゲーム開始後もUndoを繰り返せるため、必要に応じて直前ゲームまで戻れる。
5. 試合終了後も、結果画面を確定的に離れるまでは最終ポイントを取り消し、試合を再開できる。
6. Undo後はポイント履歴、スコア、ゲーム取得数、勝敗、各集計をすべて再計算する。
7. UndoのRedoは提供しない。

### 3.7 試合中画面

通常時は次の優先順で大きく表示する。

1. 現在のゲーム番号
2. 記録対象選手名、対戦相手名、現在スコア
3. 「得点」「失点」
4. 「1点戻す」
5. 「試合の確認」

分類選択中は、現在選択している得点／失点と分類階層を明示する。

### 3.8 試合の確認

- 現在のゲーム番号とスコアを表示する。
- 現在までの全ポイントを新しい順または古い順に一貫して表示する。
- 各ポイントにはゲーム番号、記録後スコア、得点／失点、大分類、詳細分類を表示する。
- 内容は読み取り専用とし、分類修正や任意削除はできない。
- 閉じる操作で、未確定の入力状態を壊さず試合画面へ戻れる。

### 3.9 試合終了後

#### 試合結果

- 勝敗
- 記録対象選手名と対戦相手名
- 試合日時
- ゲーム取得数
- 各ゲームの最終スコア

#### ゲーム別集計

- ゲームごとに、得点の各大分類件数を表示する。
- ゲームごとに、失点の各大分類件数を表示する。
- 0件の分類も0として表示する。

#### 全体集計

- 試合全体の得点を、大分類ごとの件数と構成比で表示する。
- 試合全体の失点を、大分類ごとの件数と構成比で表示する。
- 分母が0件の場合、構成比は0%として表示する。

#### ポイント履歴

全ポイントを時系列で表示する。

表示例：

```text
G1 1-0　得点 → サーブ → エース
G1 1-1　失点 → レシーブミス → オーバー
G1 2-1　得点 → 3球目 → フォアドライブ
```

### 3.10 過去試合

1. 完了した試合を端末内に保存する。
2. 一覧には試合日時、選手名、対戦相手名、勝敗、ゲーム取得数を表示する。
3. 初期表示順は試合日時の新しい順とする。
4. 一覧から、試合終了後と同じ詳細画面を再表示できる。
5. 進行中の試合は完了済み一覧とは区別して保存する。

### 3.11 オフライン動作

- 初回読み込み後は、ネットワーク接続なしで試合開始、記録、保存、閲覧ができる。
- PWAとしてホーム画面へ追加できる。
- アプリ更新時も、保存済み試合データを失わない。
- ブラウザデータを利用者が消去した場合、データを復元できないことを明示する。

## 4. Data Model

スコアと集計値はポイント列から再計算可能にする。保存した各ポイントの`scoreAfter`は表示・監査用のスナップショットとする。

```ts
type PointOutcome = "won" | "lost";

type MatchStatus = "in_progress" | "completed";

interface Match {
  id: string;
  playerName: string;
  opponentName: string;
  startedAt: string;
  completedAt: string | null;
  status: MatchStatus;
  points: Point[];
}

interface Point {
  id: string;
  sequence: number;
  gameNumber: number;
  outcome: PointOutcome;
  category: string;
  detail: string | null;
  scoreAfter: {
    player: number;
    opponent: number;
  };
  recordedAt: string;
}
```

### 4.1 永続化

- IndexedDBを使用する。
- DBスキーマにはバージョン番号を持たせ、将来の変更時にマイグレーションできるようにする。
- 1ポイント確定またはUndoするたびに、進行中試合を保存する。
- 完了時は同一の試合IDを維持したまま`completed`へ変更する。

## 5. Non-Functional Requirements

### 5.1 操作性

- 得点／失点ボタンは片手でも押しやすいタップ領域を確保する。
- 主要タップ領域は最小44×44 CSS pxとする。
- 得点と失点は、色だけに依存せずテキストと形でも区別する。
- 主要操作は縦持ちスマートフォン幅360px以上で横スクロールなしに利用できる。
- ポイント確定後、次のポイントを入力できる状態へ即座に戻る。

### 5.2 性能

- 対応端末上で、タップからポイント表示更新まで100ms以内を目標とする。
- 1試合200ポイントの履歴でも、入力操作に体感上の遅延を発生させない。
- 初回読み込み後のオフライン起動を可能にする。

### 5.3 信頼性

- 画面再読み込みやブラウザ再起動後も、進行中の試合を復元できる。
- スコア、勝敗、集計はポイント履歴を唯一の根拠として再計算する。
- 保存エラー時は成功したように見せず、記録者へ再試行可能な通知を出す。

### 5.4 アクセシビリティ

- WCAG 2.2 AA相当のコントラストを確保する。
- キーボード操作とスクリーンリーダーで主要フローを利用できる。
- フォーカス表示を消さない。

## 9. Code Style

- ドメイン型、コンポーネントはPascalCaseを使用する。
- 変数、関数、フックはcamelCaseを使用する。
- 定数は意味のある名前にし、分類文字列を画面へ直書きしない。
- スコア計算などのドメインロジックはReactコンポーネントから分離し、純粋関数にする。
- 不変更新を行い、引数を破壊的に変更しない。
- UI文言は日本語、コード識別子は英語とする。

```ts
export function isGameComplete(playerScore: number, opponentScore: number): boolean {
  const leaderScore = Math.max(playerScore, opponentScore);
  const scoreDifference = Math.abs(playerScore - opponentScore);

  return leaderScore >= 11 && scoreDifference >= 2;
}
```

## 10. Testing Strategy

### 10.1 Unit

Vitestで`src/domain`のルールを重点的にテストする。

- 11-0、11-9でゲーム終了
- 10-10、11-10では継続
- 12-10、15-13でゲーム終了
- 3ゲーム先取で試合終了
- ポイント列からのスコア・集計再計算
- Undo後のゲーム／試合状態復元
- 全分類の定義とタップ数

### 10.2 Component

React Testing Libraryで次を確認する。

- 得点／失点から分類確定までの遷移
- 2タップ項目と3タップ項目
- 未入力の選手名バリデーション
- ゲーム終了表示と次ゲーム移行
- 試合中確認画面の読み取り専用表示
- 保存エラー表示

### 10.3 Integration

- ポイント入力、IndexedDB保存、再読み込み復元
- 連続Undoと永続データの整合性
- 完了試合が過去試合一覧と詳細へ反映されること
- DBバージョン更新時に既存データが維持されること

### 10.4 E2E

Playwrightのモバイルビューポートで次の主要経路を確認する。

- 試合開始から3ゲーム先取、結果保存まで
- 10-10からデュース終了まで
- ゲーム終了をまたぐ連続Undo
- オフライン状態での試合記録と履歴閲覧

### 10.5 品質基準

- ドメインロジックは分岐カバレッジ90%以上
- プロジェクト全体は行カバレッジ80%以上
- `lint`、`typecheck`、`test`、`build`、主要E2Eがすべて成功する

## 11. Boundaries

### Always

- ポイント履歴をスコアと集計の唯一の根拠にする
- 入力値とIndexedDBから読み出したデータを検証する
- 挙動変更はテストを先に追加または更新する
- 実装タスク完了時にlint、型検査、関連テストを実行する
- タップ数上限とスマートフォンでの操作性を維持する
- 仕様変更時はコードより先に本書を更新する

### Ask first

- 分類名、分類階層、試合ルールの変更
- IndexedDBスキーマの破壊的変更
- 新しいランタイム依存関係の追加
- 初版対象外機能の追加
- CI設定、デプロイ先、対応ブラウザ範囲の変更

### Never

- 秘密情報や個人情報をリポジトリへコミットしない
- 保存済み試合を同意なく削除または上書きしない
- スコアや勝敗とポイント履歴が矛盾した状態を保存しない
- 失敗するテストを承認なく削除または無効化しない
- アプリから課題、敗因、練習内容を断定・提案しない
- `node_modules`や生成物を直接編集しない

## 12. Success Criteria

- 全分類について、1点を仕様どおり2タップまたは3タップで確定できる。
- 360px幅の画面で、主要記録操作に横スクロールが発生しない。
- 通常ゲームとデュースの終了条件が正しく判定される。
- 3ゲーム先取で試合が自動終了する。
- Undoを連続実行でき、ゲーム／試合終了をまたいでも状態が正しく復元される。
- 再読み込み後に進行中試合を継続できる。
- 試合結果、ゲーム別集計、全体集計、ポイント履歴が記録内容と一致する。
- 完了試合が過去試合一覧に表示され、詳細を再閲覧できる。
- 初回読み込み後、オフラインで主要機能を利用できる。
- アプリ内に自動分析・練習提案の文言や機能が存在しない。
- 定義した品質コマンドがすべて成功する。
